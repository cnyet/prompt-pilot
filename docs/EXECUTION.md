# PromptPilot 执行方案

> 这份文档回答四件事：技术方案怎么分层、任务怎么编排、多个角色怎么并行、本地插件与子 agent 怎么用。

## 一、技术方案

一句话：**Next.js 15 单体应用，四层结构，主路径只调一次模型。**

| 层 | 位置 | 职责 | 关键约束 |
|---|---|---|---|
| 界面层 | `app/` `components/` | RSC 渲染外壳，客户端组件负责交互；用 `fetch` 读 SSE | 密钥永不进客户端；长列表按需虚拟化 |
| 引擎层 | `lib/engine/` | 五阶段：compose / harden / interview / evaluate / refine；纯函数优先 | 每个阶段有明确输入输出类型，可单测，可替换 |
| 适配层 | `lib/llm/` | `LLMProvider` 接口，四个实现：Ark / OpenAI 兼容 / Mock / heuristic | Ark 扩展字段在 provider 内收口，不外泄 |
| 数据层 | `prisma/` `lib/db/` | SQLite + Prisma；`LlmCall` 是成本账本 | 流式过程中不写库，落库放 `finally` |

三条贯穿全局的硬约束：

1. **主路径一次模型调用**：`compose` 内含意图判别与假设清单；`harden` 是确定性补丁；`evaluate` 手动触发。
2. **写入规则唯一**：文档只有四个写源，仲裁规则见 `ARCHITECTURE.md` 6.6，手改字段永不被自动覆盖。
3. **降级可用**：L1 离线模式用 heuristic composer 生成骨架，无 key 也能走完全流程。

## 二、任务编排

编排单位不是"层"，是**可验收的垂直切片**。每个切片从界面到数据库打通，能独立演示。

```
切片的固定结构：
  任务 = 一个用户可见的结果 + 一组验收编号（AC-x）
  例子：M1 = "输入一句话拿到流式八字段" + AC-1 / AC-15 / AC-16
```

任务板机制：

| 机制 | 用法 |
|---|---|
| `team_task_create` | 建任务，写清验收标准与允许改的目录 |
| `blocked_by` | 声明依赖，未满足时不可开工 |
| `write_scopes` | 声明预计改动的路径前缀，用来发现冲突 |
| `claim` / `complete` | 带 revision 的乐观锁，避免两人改同一任务 |

**编排顺序**：先冻结接口，再并行；先跑通一条细线，再铺开。

冻结的三样东西（冻结前不开并行）：

1. `lib/llm/types.ts`：`LLMProvider` 与请求响应类型
2. `lib/engine/schema.ts`：`PromptPilot Schema v1`（Zod）
3. SSE 事件协议：`stage` / `field` / `delta` / `lint` / `assumption` / `usage` / `error` / `done`

## 三、多角色并行

### 角色与写作用域

| 角色 | 拥有 | 不碰 | 产出 |
|---|---|---|---|
| **Lead（我）** | 架构决策、接口冻结、集成、最终审阅、跑全量测试 | 具体业务代码 | 契约、合并、验收结论 |
| **后端 agent** | `lib/llm/` `lib/engine/` `app/api/` | `app/(workspace)/` `components/` | 适配层、引擎、路由 |
| **前端 agent** | `app/(workspace)/` `components/` | `lib/engine/` `prisma/` | 页面、编辑器、流式渲染 |
| **测试 agent** | `tests/` `fixtures/` | 业务实现 | 单测、E2E、故障画像 |
| **评审 agent（只读）** | 无写权限 | 全部 | 对照 `DESIGN.md` 禁令与 `REVIEW.md` 问题闭环表 |

### 并行规则

1. **写作用域不相交**。这是约定不是锁：写作用域重叠仍可能互相覆盖，所以并行时按目录切，不按文件切。
2. **只并行的三件事**：后端实现、前端实现、测试用例。其余（契约、集成、依赖升级）串行。
3. **各自先跑自己的测试**，Lead 合并后再跑全量。合并前必须由 Lead 看 diff，不能直接信任 agent 的"已完成"。
4. **汇合点检查**：接口签名一致、事件名一致、错误码一致。三样任一不一致就停下来对齐，不"先跑起来再说"。

### 建议的并发度

3 到 4 个写入角色是上限。再多，Lead 的审阅带宽会变成瓶颈，而且是静默瓶颈：文件改得更快，但没人验证。

## 四、本地插件怎么调

本地插件在本环境里就是 **skill**，放在 `~/.agents/skills/`，目前 40 个。

调用方式：`skill({ name })` 加载完整指令，然后按指令执行。三个要点：

1. **插件不会自动生效**。看到一个匹配的任务，必须显式加载，否则等于没用。
2. **先加载再动手**。加载前不知道它要求什么（例如 `impeccable` 有强制的前置检查与设计禁令）。
3. **插件目录是本地文件**，可以读、可以改，改完下次加载即生效。

本项目会用到的：

| 插件 | 用在哪 |
|---|---|
| `prompt-optimization` | 16 条诊断规则的语义依据、系统提示词写法 |
| `impeccable` | 设计令牌落地、组件状态补齐、界面评审（有强制的前置门禁） |
| `tdd` / `test-generator` | 引擎纯函数与诊断规则的单测 |
| `code-review` | 每个里程碑合并前的标准与规格双轴评审 |
| `agent-browser` | E2E 验收时开浏览器自查真实渲染，不靠想象 |
| `office-*` | 导出交付物（只在需要 docx/pptx 时用） |

## 五、子 agent 怎么选

四种手段，按"要不要我的上下文"和"规模"两个维度选：

| 手段 | 上下文 | 适用 | 不适用 |
|---|---|---|---|
| `subagent` | 独立，全新 | 自包含的调研、单文件实现、独立验证。**给什么它就知道什么**，任务必须自带全部输入 | 需要本次对话历史才能做对的事 |
| `subagent_fork` | 继承本对话历史 | "基于刚才的讨论继续做"、评审我自己的产出、延续性重构 | 历史很长时成本高 |
| `workflow` | 脚本编排多个 agent | 大规模扇出：审计 50 个文件、批量迁移、多角度交叉验证。带 `pipeline` 无屏障串联、`parallel` 屏障、schema 校验 | 一两个任务，不值得写脚本 |
| `spawn_teammate` | 常驻、多次对话、共享任务板 | 长期多角色并行开发 | 一次性任务，用 `subagent` 更轻 |

配套动作：`send_message` 中途改方向，`wait_agent` 等变更（不轮询），`interrupt_agent` 打断跑偏的角色。

**一条纪律**：子 agent 的输出是"待验证的结论"，不是"已完成的事实"。Lead 必须自己看 diff、跑测试，再决定采信。

## 六、M1 的实际编排示例

```
Lead：冻结 types.ts / schema.ts / SSE 协议（串行，1 小时）
   │
   ├─ 后端 agent ── ArkProvider（含 include_usage、reasoning_content、thinking 关闭）
   │                 Mock 七种故障画像
   │                 LlmCall 账本 + 错误分级重试 + requestId 幂等
   │
   ├─ 前端 agent ── 中栏八字段块、流式填充、插入符、停止保留
   │                 假设 chip 与"只重算受影响字段"
   │
   └─ 测试 agent ── 故障画像 fixtures、兜底链测试、SSE 事件序列合法性
   │
汇合：Lead 对照 AC-1 / AC-15 / AC-16 验收，跑全量，看 diff，再进 M2
```

三个角色同时改，但目录不重叠：`lib/llm|lib/engine|app/api` 与 `app/(workspace)|components` 与 `tests`。

## 七、边界与已知风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 写作用域只是约定 | 两个 agent 同时改同一文件，后者覆盖前者且无报错 | 按目录切分；Lead 合并前读 diff；关键文件（类型、Schema）只由 Lead 改 |
| 子 agent 缺乏上下文 | 它看不到本次对话，容易"答得很对但不是我们要的" | 任务描述自包含，附上必要的文档片段与验收编号 |
| 并行不等于更快 | 4 个 agent 同时产出，审阅时间线性增长 | 并发上限 3 到 4；每个切片小到能在一轮内审完 |
| 插件质量参差 | 40 个插件里有的是通用方法论，有的专为别的项目 | 只用与本任务直接相关的；加载后先看它的前置条件 |
| 回归成本 | 并行合并后问题定位变难 | 每个切片结束跑全量测试；不让未验证的代码进入下一个切片 |
