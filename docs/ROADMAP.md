# PromptPilot 实施计划

> 估算单位：人日，按"1 名开发者 + AI 辅助"的节奏。**总计 24 到 30 人日**（评审前的 13 人日被低估约一倍，明细见 `REVIEW.md` 2.10）。
> 每个里程碑都是**可验收的垂直切片**，不是"写完了某一层"。

## 零、先做 6 人日可演示版

不要一次做完 24 人日。先切一个能验证核心假设的最小闭环：

| 包含 | 人日 | 能验证什么 |
|---|---|---|
| M0 骨架 | 1 | 设计是否成立 |
| M1 精简（compose 加四级兜底，不做错误分级细化） | 2 | 生成质量够不够，一次通过率有没有 50% |
| M2 精简（文档状态模型加假设 chip，不做深度访谈） | 1.5 | 不打断的路径是否顺畅 |
| M3 诊断 | 1.5 | 16 条规则是否符合直觉 |

产出：输入一句话 → 八字段 → 实时诊断 → 复制导出。没有库、没有评估、没有补丁。

**核心假设没验证前不要进 M4 到 M6。** 如果一次通过率低于 30%，说明八字段结构或生成质量有问题，此时做评估系统是给一个不好用的东西加仪表盘。

### M1 模型适配层与结构化生成（3.5 人日）

**任务**
1. `LLMProvider` 接口与注册表（见 `ARCHITECTURE.md` 第四节）。
2. `ArkProvider`：**基于 `openai` npm 包改 `baseURL`**（方舟没有 Node SDK，别去找）；流式默认带 `stream_options.include_usage`；`delta.reasoning_content` 单独映射到思考区；`thinking` 默认关闭（doubao-seed-2.1 系列默认是开的）；`maxTokens` 内部择一下发 `max_tokens` 或 `max_completion_tokens`。
3. `MockProvider` 加**故障注入画像**（valid / bad_json / fenced_json / truncated / rate_limited / quota_exceeded / slow）。只吐正确答案的 Mock 测不到四级兜底链，这条是 NFR-11 的验收前提。
4. **heuristic composer**（L1 离线模式）：确定性模板生成八字段骨架，与 LLM 版实现同一个 `Composer` 接口。
5. `PromptPilot Schema v1` 的 Zod 定义（八字段），前后端共用。
6. `compose` 阶段：一次调用同时产出 `_intent`（含生成/改进判别与假设清单）与八字段正文，流式。
7. SSE 路由 `POST /api/engine/generate`，事件协议按第五节实现。
8. 中栏结构化视图：字段块、流式填充、插入符、停止按钮、中断保留。
9. `LlmCall` 账本：每次模型调用落库（阶段、模型、耗时、首字延迟、输入输出 token、缓存命中 token、思维链 token、金额、`finish_reason`、重试次数、`traceId`）。成本面板与 NFR-10 的唯一数据源，引擎各阶段的调用也必须进这个账本。
10. 错误分类与退避重试：只对限流类 429 与 5xx 重试（指数退避加随机抖动，最多 3 次）；`QuotaExceeded`、`AccountOverdueError`、`ServiceNotOpen`、参数类 400 直接抛业务错误，不做无意义重试，也不能把业务错误吞成网络错误。
11. 每个阶段显式设置 `thinking`（2.1 全系默认开启，结构化改写任务要关掉）；用 `promptId` 作 `prompt_cache_key` 提升隐式缓存命中率。
12. **幂等**：`requestId` 加内存 LRU 去重，双击只产生一次请求与一个版本。

**验收**：对照 AC-1、AC-15、AC-16；MockProvider 与 ArkProvider 可切换且界面行为一致；`Esc` 中断后已生成字段仍可编辑；按住故障画像逐个跑通四级兜底链；错误码分级有单元测试覆盖。

**执行期补充（2026-11-09）**：provider 层完成后发现，有 Key 的路径是"拿完整 JSON 再回放"，首字延迟等于全长，且用量与思维链没有事件通道。已从工单 05 拆出**工单 15（真流式与用量透传）**，约 1.5 人日，并入 M1。M1 实际约 5 人日，总计划相应上调到约 26 人日。

### M2 假设 chip、文档状态模型、字段编辑器（3.5 人日）

**任务**
1. `intent` 阶段：输出任务类型、领域、目标读者、交付物、缺失槽位、歧义点（带严重度）。
2. `clarify` 阶段：2 到 3 个问题（硬上限 5），每题带推荐默认值与一键采纳。
3. 左栏：需求输入框、澄清问题条、跳过、历史输入。
4. 假设条：跳过的项在结果区顶部显式列出，导出时可选择剔除。
5. 字段编辑器：八字段独立编辑、实时重渲染、来源标记、单字段操作（重新生成 / 加长 / 缩短 / 更具体）。
6. 变量声明区：`{{variable}}` 解析、类型、默认值、必填、枚举。
7. 撤销重做栈（≥ 50 步）。
8. 三视图切换：结构化 / 渲染文本 / JSON。

**验收**：对照 FR-1.*、FR-3.*；手工改了某字段后点"重新生成"，只重生成该字段且其他字段不动；跳到澄清不损失任何已输入内容。

### M3 本地 lint 与诊断面板（1.5 人日）

**任务**
1. 规则引擎：R001 到 R014（见 `ARCHITECTURE.md` 第六节），纯函数、零 IO。
2. 每条规则配单元测试，含正例与反例。
3. 右栏诊断面板：error / warn / info 分组、计数徽标、问题定位（点击滚动并选中）。
4. 一键修复（可自动修复的规则）与"应用全部修复"。
5. 编辑防抖 150ms，保证输入不掉帧。
6. 规则触发位置在编辑区做波浪下划线标注。

**验收**：对照 AC-3、AC-4、NFR-3；在 4000 字提示词上 lint 单次 < 50ms（用性能测试断言）；规则单测覆盖率 > 90%。

### M4 试运行、输出评估、定向优化（4 人日）

**任务**
1. `POST /api/run` 流式试运行，参数可选（temperature、max_tokens、thinking）。
2. 变量表单自动生成（枚举给下拉、长文本给多行），变量值可存为变量集复用。
3. 试运行区：输出区、耗时、token、费用实时累加、可取消。
4. 运行历史按版本归档。
5. `evaluate` 阶段：按 `successCriteria` 逐条判定输出（满足 / 部分 / 不满足），带判定锚点示例；可选与 v0 盲评。
6. 判定面板：成功标准逐条判定、判定理由、人工改判、重新判定。
7. `refine` 阶段：依据选中的 lint 项或未达标的成功标准产出**最小改动补丁**，不覆盖用户手改字段。
8. diff 视图：行内与并排两种模式，行级加词级双层高亮。
9. 逐字段接受 / 拒绝，全部接受 / 全部放弃；接受后生成新版本。

**验收**：对照 AC-5、AC-7、AC-8、FR-5.*、FR-6.1 到 6.2、FR-7.1 到 7.3；手工改过的字段在优化后必须保持原样（写进自动化测试）。

### M5 提示词库、版本管理、导入导出（2 人日）

**任务**
1. 提示词 CRUD、标签、描述、归档、收藏、最近使用。
2. 全文检索（标题、描述、标签、正文、变量名），SQLite FTS5 或 Prisma 全文方案。
3. 列表与卡片双视图，排序过滤。
4. 版本模型：单调递增版本号、来源、变更摘要、父子关系。
5. 版本时间线（含每次的胜率变化）、任意两版本 diff、回滚（生成新版本不破坏历史）。
6. 导出六种格式，变量占位符按目标格式转换（可配置）。
7. 批量导出（按标签或全量）。
8. 导入 Markdown / JSON，尝试反解析，失败则纯文本导入并提示。

**验收**：对照 AC-9、FR-8.*、FR-9.*；导出的 OpenAI messages JSON 能直接粘贴进官方 SDK 跑通（写一条集成测试）。

### M6 评估对比与成本可观测（1.5 人日）

**任务**
1. `EvalTask` 与 `CriterionCheck` 模型：模式（基线对比 / 多样本批量）、冻结的成功标准清单、版本集合、样本数、状态。
2. 批量执行器：N 版本 × M 样本网格运行，支持取消与断点续跑。
3. 成功标准判定表，按条逐条展示各版本是否满足。
4. 盲评 GSB：隐藏版本标识、位置随机化、双向交换消除位置偏见、胜率统计。
5. 评估详情页：一句话结论 + 成功标准判定表 + 样本输出原文。不使用雷达图。
6. 成本面板：按模型、按阶段、按天、按提示词聚合 `LlmCall`，展示 token、缓存命中率、思维链 token 占比与金额（人民币）。价格表放 `AppSetting` 可配，改价后可重算。

**验收**：对照 AC-6、FR-6.3 到 6.5；同一评估任务重复执行，判定差异在可接受范围内；位置随机化在测试中可验证（同一对样本交换后胜率不反转）。

### M7 硬化与打磨（1.5 人日）

**任务**
1. 补齐组件状态矩阵中所有缺失状态（逐个核对 `DESIGN.md` 第五节）。

7. 部署说明、`.env.example` 完善、离线行为验证。

## 五、交付顺序与评审点

每个里程碑结束后暂停，做一次对照验收清单的自查，然后请你过一遍再进下一个。四个关键评审点：

1. **M1 后**：生成质量与流式体验。如果八字段结构本身就不合用，这时候改代价最小。
2. **M3 后**：lint 规则是否符合你的直觉。规则集是产品判断力最集中的地方。
3. **M5 后**：库与导出的信息架构。这一步决定了产品是玩具还是资产。
4. **M7 后**：整体打磨与发布检查。
