# 16 — 单字段重算不得静默丢弃内容

**What to build:** 用户手动改过格式的字段，在点「加长 / 缩短 / 更具体 / 重新生成」时不会丢掉原有内容。凡是无法被结构化路径识别的行，要么原样保留在结果里，要么让操作直接拒绝并说明原因，绝不允许无声消失。

**Blocked by:** 03 — 字段编辑器与单字段重算

**Status:** ready-for-agent

- [ ] 输入一段含无法解析行的字段文本，执行「缩短」后这些行仍然存在（或整次操作被拒绝且原文不变）
- [ ] 规范格式下行为不变：仍然得到 65 → 58 这类合理的缩减
- [ ] 操作无法保全时给出明确提示，说明哪几行不能处理，并保留原文
- [ ] 有测试覆盖：非规范输入 + 四种操作，断言操作前后内容行集合的包含关系
- [ ] 假设 chip 走同一套写回路径时也受此保护（不因改 `output.language` 而截断整段文本）

## Comments

### 2026-11-09 Lead 复核工单 03 时发现

复现方式：把 `output` 字段改成非规范格式后点「缩短」。

输入五行：

```
格式：Markdown
章节：标题、正文、要点摘要
长度：400 到 800 字
语言：中文
语气：专业、克制、直接
```

输出只剩一行 `格式：Markdown`，其余四行静默丢失。

根因：重算链路是「解析成结构化叶子 → 应用操作 → 重新渲染」，无法映射的行在解析阶段就被丢弃，重渲染自然不带它们，且全程没有提示。

为什么重要：这个产品的编辑器允许用户随便改字段文本，用户改过的往往正是最需要保留的内容。一次「缩短」把用户刚写的两句话删掉，比不缩短伤害大得多。工单 04 的假设 chip 也用同一套路径写回，不修就会同样截断。

建议方向（实现者自行判断）：操作前做一次往返校验，若重渲染结果不能覆盖原文的非空行，则降级为行级文本操作（只增删受操作影响的段落），或直接拒绝并提示。
